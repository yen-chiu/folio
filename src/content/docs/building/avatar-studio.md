# Avatar Studio · 私人头像工坊

> 让头像更换成为一次可预览、可确认、可回退的发布，而不是反复手工修改仓库。

- **项目名称**：Avatar Studio
- **归属**：YenChiu / Vesper 生态，Folio 负责项目文档
- **项目性质**：私人管理工具；不是公开博客功能或面向访客的账号系统
- **项目立项日期**：2026-11-23
- **开发仓库**：[yen-chiu/yen-chiu.github.io](https://github.com/yen-chiu/yen-chiu.github.io)
- **隔离分支**：[feature/avatar-studio](https://github.com/yen-chiu/yen-chiu.github.io/tree/feature/avatar-studio)
- **当前状态**：独立分支已提交早期实现；尚未完成 Cloudflare Access 配置、真实部署、端到端验收；**不代表已上线**
- **发布原则**：开发分支不自动合并 `main`；管理页只有授权账号登录后才能访问；更新网站头像必须再次确认

## 一、背景与问题

Vesper 当前使用透明 PNG 头像。已有生成脚本可以从 `src/assets/avatar.png` 输出动画文件，但此前的 GIF 转换暴露出透明轮廓色边、调色板量化和逐帧缩放等问题。现有更新流程也依赖直接修改 GitHub 仓库，不便于检查最终效果。

Avatar Studio 的目标是将**更换头像**变成一个独立、可审查的发布工作流：在受保护的管理界面选择 PNG，预览动画，然后主动确认提交。头像素材的公开发布与博客本身的部署仍保持现有 GitHub Pages 流程。

### 本期明确要解决

1. 免去日常手动替换头像源码文件的操作。
2. 避免“PNG → GIF → WebP → GIF”等反复有损转换。
3. 避免头像未确认就被公开发布。
4. 避免把带仓库写权限的令牌暴露在浏览器或静态站点。
5. 保证管理工具升级不干扰 Vesper 主站运行。

### 本期不做

- 不开放访客注册、公共上传、头像共享平台。
- 不向浏览器暴露 GitHub Token，也不使用前端静态密码代替身份认证。
- 不声称一张静态 PNG 可以自动生成真实眨眼、表情或发丝独立运动；第一期只做非生成式轻微浮动。
- 不提供未经测试的“预览就是最终编码文件”保证：本期预览和最终资产的阶段性差异必须明确标注。

## 二、系统边界与架构

| 系统 | 部署位置 | 源码与职责 | 公开状态 |
| --- | --- | --- | --- |
| Vesper 主站 | `yenchiu.com` / GitHub Pages | `main`：公开博客、静态头像与动画资产展示 | 公开 |
| Avatar Studio | 独立 Cloudflare Worker，建议专用域名 `studio.yenchiu.com` | `feature/avatar-studio`：管理页、登录校验、上传和发布 API | **仅授权账号** |
| 图片生成 | Vesper 的 GitHub Actions | 从原始 PNG 的同一套 RGBA 动画帧分别生成 Animated WebP 与 GIF | 生成产物公开 |
| 项目记录 | Folio | 本项目书、实施阶段与验收规则 | 公开文档；**不含秘密配置** |

管理工具的开发分支与主站部署可以长期并行，但它们并不是“两条分支自动各自上线”。只有完成 Cloudflare Worker 部署与 Access 配置后，Studio 才能实际运行。

### 发布数据流

```text
单一授权账号通过 Cloudflare Access 登录
                  ↓
       Avatar Studio 私有 Worker
                  ↓
           上传 PNG 到浏览器
                  ↓
         本地静态 / 动效预览
                  ↓
          人工确认「设为头像」
                  ↓
Worker 再验证登录、请求来源、文件格式
                  ↓
GitHub API 仅更新 main/src/assets/avatar.png
                  ↓
Vesper 的 GitHub Actions 构建并验证
                  ↓
  静态 PNG + Animated WebP + GIF 发布
```

**关键边界**：开发代码留在分支，不自动合并；发布行为会明确修改主站 `main` 的特定头像资源。这两件事不能混为一谈。

## 三、功能范围与交互

### A. 私人登录

- 独立地址，不放在公开 GitHub Pages 的 `src/pages` 或 `public` 目录。
- Cloudflare Access 的允许策略限制为**一个指定的账号邮箱**，不得向任意 GitHub / Google 登录用户开放。
- Worker 自身必须再次核验 Access 签名令牌，包括签名、签发者、目标应用、有效期和允许邮箱；不能只相信前端传来的身份字段。
- 未登录、登录错误、身份令牌无效或后台配置不完整时一律拒绝访问。
- 管理端的完整路径，包括写入 API，都必须受相同保护；不得通过未受保护的预览域名或 `workers.dev` 旁路访问。

### B. PNG 上传与检查

- 第一期只接收 PNG，建议正方形透明头像。
- 前端先校验类型、尺寸、大小并展示错误原因；Worker 复核基础格式。
- 第一版接口约束：正方形、边长 128–2048px、文件不超过 4 MiB。
- 未确认发布前，图片仅在浏览器本地预览，不上传到公开博客。
- 长期应补充完整 PNG 解码、像素限制、非法文件与异常压缩数据测试；仅检查文件头不足以视作完整安全验收。

### C. 预览

- 并列显示静态 PNG 与非生成式轻微浮动效果。
- 保持人物五官、发色、服装、姿态和原始绘画风格；不凭空生成眨眼或面部变化。
- 支持系统减少动画偏好；必要时回退为静态。
- **当前阶段为浏览器 CSS 动效模拟**，不是最终 GIF/WebP 实际编码文件的逐帧解码预览。正式上线验收时，必须明确该限制，或实现真实成品预览后再修改说明。

### D. 双格式导出

唯一源文件为 `src/assets/avatar.png`，从其生成同一套 RGBA 动画帧，再分别导出：

- **Animated WebP**：网站动态头像的首选格式，保留半透明边缘；
- **GIF**：兼容与分享用，使用统一调色板降低彩边；
- **静态 PNG**：保留原始资源与关闭动态效果时的回退。

禁止把 GIF 作为 WebP 的输入再二次转码。生成脚本和产物应有可重复性测试，至少覆盖尺寸、帧数、循环、透明度、文件有效性和浏览器可显示性。

### E. 确认发布

- 确认按钮前显示明确警示：发布将替换网站公开头像，并触发主站构建。
- 二次确认后才向 Worker 发送图片字节。
- Worker 只允许更新固定仓库 `yen-chiu/yen-chiu.github.io`、固定分支 `main`、固定路径 `src/assets/avatar.png`。
- GitHub Token 只存于 Worker Secret，最小化为当前仓库 Contents 读写权限；不出现在源码、文档、页面源码或客户端请求里。
- 发布后显示真实 GitHub 提交 ID，并提供部署状态入口；**不能把“已提交”显示为“已部署成功”**。
- 当主站部署失败时，应有清楚的失败反馈与手动恢复路径，不能假定自动回滚已经实现。

## 四、安全与隐私要求

1. **默认拒绝**：未配置登录服务或密钥时，Worker 不提供可用的公开管理页。
2. **服务端鉴权**：全部路由，包括上传 API，必须验证 Cloudflare Access；不能靠隐藏 URL、`robots.txt` 或前端按钮权限。
3. **身份最小化**：只允许明确指定的账号，不记录或公开账号真实姓名；公开文档不写邮箱或任何令牌。
4. **请求防护**：验证请求来源、方法、内容类型、体积、图片尺寸，并限制可写仓库路径；发布必须显式确认。
5. **凭据隔离**：GitHub 写入令牌必须放 Cloudflare Worker Secret；不得写入 GitHub Actions 日志和公共资源。
6. **图片来源**：上传内容仅在确认时提交；不接入无必要的第三方图像识别或生成服务。
7. **权限回收**：提供撤销令牌、停用 Access 应用和关闭 Worker 的操作程序。

**项目安全验收不是“代码里写了鉴权”就完成。** 必须在真实部署中检查未登录、错误登录、伪造令牌、跨来源请求、超大文件、错误格式、重复发布和过期凭据的行为。

## 五、技术实施与当前事实

当前分支已有早期实现：

- `studio/worker.mjs`：受保护的管理页面、上传和发布接口的初版；
- `studio/wrangler.toml`：Cloudflare Worker 初始配置；
- `studio/worker.test.mjs`：未授权访问和拒绝发布的基础测试；
- `studio/README.md`：部署条件和权限设置；
- `.github/workflows/avatar-studio-ci.yml`：开发分支检查工作流。

主站现有：

- `scripts/generate-avatar-gif.py`：从原始 PNG 导出 Animated WebP / GIF；
- `.github/workflows/deploy.yml`：主站构建期间生成资产；
- `src/components/InteractiveAvatar.astro` 与外观设置：静态/动态头像切换。

**未完成的事实**：真实 Cloudflare Access 应用与专用域名尚未配置；Worker 未正式部署；真实 GitHub 写入与完整端到端构建尚未验收。早期测试/代码存在不等于生产可用。

## 六、阶段计划与里程碑

| 阶段 | 工作 | 阶段完成标准 | 状态 |
| --- | --- | --- | --- |
| M0 · 立项 | 项目书、系统边界、风险与验收要求 | Folio 归档，Vesper 未来计划可查 | 进行中 |
| M1 · 开发基线 | Worker 管理界面、PNG 预览、固定路径发布、默认拒绝测试 | 分支代码审查与自动检查通过 | 初版已提交，待验证 |
| M2 · 真实身份保护 | 配置独立域名、Cloudflare Access 单账号策略、Worker Secret | 未登录和非指定账号无法访问任何接口 | 未开始 |
| M3 · 双格式与发布验收 | 使用真实 PNG 生成 WebP/GIF、检查透明边缘、确认部署状态 | 清晰度、透明度、循环、降级均通过 | 待验收 |

| M5 · 交付 | 记录实际地址、操作流程、变更与未解决问题 | 由维护者明确同意后投入日常使用 | 未开始 |

### 以后再考虑的功能

- 真正编码后的 Animated WebP / GIF 同屏预览与下载；
- 裁剪、缩放、圆形安全区域；
- 动画参数调整和更多非生成式动效；
- 头像历史版本索引、回滚操作和发布审计；
- 更完整的 favicon、社交分享图同步。

上述能力均不属于第一期“已实现”范围。

## 七、验收清单

- [ ] `feature/avatar-studio` 的自动检查完成，且没有影响 `main` 的现有部署。
- [ ] 受保护独立域名可访问；未登录、非授权账号及所有绕过路径均被拒绝。
- [ ] GitHub Token 是仅针对当前仓库的最小权限 Worker Secret，浏览器和构建日志不可读。
- [ ] 上传错误格式、损坏文件、过大文件、异常尺寸均有明确失败提示。
- [ ] 静态预览与微动态预览在桌面、移动端正常显示。
- [ ] 手动确认前不会上传或更改公开资源。
- [ ] 确认后仅更新指定的源 PNG，不修改其他文件或分支。
- [ ] 生产构建真正生成可打开、可循环、透明边缘正常的 WebP 与 GIF。
- [ ] 网站减少动画偏好及加载失败降级为静态 PNG。
- [ ] 能区分“提交成功、构建成功、网站可访问”三种不同状态。
- [ ] 发布失败有真实可执行的恢复步骤；不声称未经实现的自动回滚。
- [ ] 公开页面、SEO、说明文档均不含个人中文真实姓名或任何凭据。

## 八、主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 静态 Pages 无法安全承担私人管理接口 | Worker 独立部署，Access + 服务端签名验证 |
| 管理分支与主站分支职责混淆 | Studio 代码独立分支；头像发布只更新 main 固定路径 |
| GitHub 写入权限泄露 | 单仓库最小授权、Worker Secret、凭据轮换 |
| 预览和编码成品效果不一致 | 明确标注 CSS 预览；最终成品需在验收中实际查看 |
| GIF 边缘色彩伪影 | 直接从 RGBA 帧导出、统一调色板、人工检查成品 |
| 部署成功判定过早 | 展示提交 ID；实际部署状态另行验证 |
| 误发布或仓库资源冲突 | 确认对话框、固定写入路径、GitHub 提交可回退 |
| 管理页绕过登录 | 同时验证 Access 应用覆盖范围与 Worker 内的 JWT |

## 九、后续维护原则

- 文档只记录**已证实**的进展，未部署不写“已上线”。
- 开发变更先留在 `feature/avatar-studio`；不为了更新管理工具而自动合并主站。
- 生产用身份和授权配置由维护者在 Cloudflare、GitHub 管理，不写入公开文档。
- 发布时按 Vesper 的版本规范更新日志；尚未上线则继续保留在「在途改动」中。

---

**项目当前结论**：Avatar Studio 已具备隔离分支与基础实现，但距离“仅指定账号能登录并安全更新线上头像”仍有部署、鉴权、格式与端到端验收工作。项目书用于约束下一步实施，不构成上线证明。
